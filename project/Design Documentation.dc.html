1. Design approach

We designed the system around one rule: the patient record is the single source of truth, and every role writes to it rather than keeping a private copy. That decision drove the rest. Because every department reads the same record, an order placed by a doctor appears in the laboratory worklist without anybody re-keying it, and a verified result appears in the chart, the doctor's alert list and the patient's phone at the same moment.

The second decision was to separate what the system knows from how it looks. Domain state and the rules that change it sit in a logic layer. Screens read from that layer and call its methods. No screen keeps its own copy of clinical data. That separation is what makes the storage replacement in §9.3 possible without rewriting the interface.

Notation follows UML 2.5, simplified where full notation would add nothing for a reader.

2. System architecture

Four layers. Dependencies point downward only: presentation depends on application logic, logic depends on the domain model, and the domain reaches storage through an interface it defines itself. Nothing lower depends on anything higher, so any layer can be replaced from below.

In v2.0 the lower three layers moved out of the browser and into a FastAPI service, and the persistence layer became PostgreSQL. The diagram below is unchanged in shape because the change did not alter it: the same four layers, with a process boundary now drawn between presentation and application logic. §9.2 shows where each layer runs.

2.1 Why layered and not microservices

A hospital of this size runs one shared record with tight coupling between departments. Splitting it into services would mean distributed transactions for something as ordinary as signing a consultation, which stages a laboratory order, a prescription and an invoice line in one action. A layered design keeps that atomic and keeps the deployment simple enough for hospital IT to run. The module boundaries in §7 are drawn so a service split stays possible later if patient volume demands it.

8. Data model

Sixteen entities: fourteen drawn below, plus two log tables noted under the figure. Patient is the hub; almost everything clinical hangs off it.

8.1 Database design decisions

DecisionReason
MRN as the patient keyStaff already speak in MRNs. Using it as the primary key means no translation between what the system stores and what the folder label says.
Invoice lines as a separate tableA visit accumulates charges from several departments at unpredictable times. Separate lines let each department append without locking the invoice.
Invoice status derived, not storedStatus is a function of total and paid. Storing it invites the two disagreeing after a partial payment.
Bed occupancy as a nullable patient key on the bed rowA bed either holds one patient or none. A unique constraint on the occupied bed makes double allocation impossible at the data level, not just in the interface.
Allergies and conditions as arrays on the patientThey are read on every prescription check and never queried independently. Separate tables would cost a join on the hottest safety path.
Append-only audit tableAn audit trail that can be edited is not an audit trail. No update or delete permission is granted on it.
Orders reference the encounterEvery test, scan and prescription traces back to the consultation that ordered it, which is what an auditor or an insurer asks for.

9.2 Deployment view

NodeContents
Staff workstation or tabletBrowser running the staff workspace over HTTPS. Holds no patient data and no credential beyond a session cookie it cannot read.
Patient phoneBrowser running the patient application over mobile data or Wi-Fi.
Web tier: VercelThe Next.js application. Renders every screen, attaches the session token to its calls, and is the only origin the browser talks to.
Application tier: AWS App RunnerThe FastAPI service, from a container image in Elastic Container Registry. Publicly addressable for the web tier; its own egress runs through a VPC connector.
Data tier: Amazon RDS for PostgreSQLThe database. Its security group admits the App Runner connector and nothing else, so no address range on the internet can reach port 5432.
AI endpoint: Amazon BedrockReached from the application tier only, over the AWS network, authorised by the App Runner instance role.

The browser reaches exactly one origin. It never holds a database credential, an AI key, or even the address of the API. Every call it makes is relative to the web tier, which forwards it.

9.3 The migration, as carried out

Version 1.0 persisted to browser storage, so a record did not follow a patient between devices. The SRS declared this as CON-05. The five steps below are the plan the previous revision of this document set out, with what was actually done against each.

StepPlannedDelivered
1Create the schema in figure 9 as PostgreSQL tables with the constraints listed in §8.1.As specified. Sixteen tables, with the double-booking index, the one-patient-per-bed index, the forward-only order triggers and the generated invoice status.
2Move staff accounts to a managed authentication service; map RoleEnum onto row-level security policies so authorisation is enforced by the database rather than only the interface.Changed. Accounts are rows in a users table with argon2id hashes, and authorisation is enforced by guards on API routes rather than by database policies. §9.4 gives the reasoning, and says what carries the guarantee instead.
3Write a second adapter satisfying the same repository interface, calling REST endpoints instead of browser storage.As specified. HttpRepository satisfies the same interface over HTTP.
4Switch the adapter at the single point where it is constructed.As specified, and the claim held: one line changed, and no screen, domain class or application component changed with it.
5Move the AI calls behind a server route so the API key is never exposed to the client.Done, and then taken further: there is no API key at all. The six prompts and the model call live in the application tier, which reaches Bedrock through its instance role.

The reason step 4 was a swap and not a rewrite is the dependency direction in figure 1. The repository interface belongs to the domain, so the domain neither knows nor cares which adapter satisfies it. That interface has now been satisfied three different ways without a screen changing.

9.4 Where authorisation lives, and why it moved

The previous revision planned to enforce authorisation with PostgreSQL row-level security. That plan was implemented, tested against a real database, and then deliberately replaced. Both approaches were built, so the comparison below is between two things that worked rather than between one that worked and one that was imagined.

ConsiderationRow-level securityGuards in the application tier
Enforcement pointThe database. A query that should return nothing returns nothing, whatever issued it.A dependency on every route. A route without one is a data leak rather than a bug.
ReachOnly clients connecting as the end user. A service connecting as one database user gets no protection from it at all.Every caller, because every caller arrives through the API.
LegibilityPolicies in SQL, one per table per operation, whose interaction is hard to read whole.Role sets in one module, named on each route beside the handler they govern.
Failure mode met in practicePolicy helper functions recursed without bound during query planning rather than execution, so every query failed with stack depth limit exceeded. Two further defects left a trigger silently unable to fire.A missing guard is invisible until something tests for it, which is why the test suite named below is part of the design rather than an afterthought.

The decision follows the architecture rather than the other way round. Once the clients are a server-rendered web tier and, in future, an integration or a native application, they all arrive through one API, and an authorisation model that protects only direct database connections then protects nothing that actually exists. The API became the single door, so the lock went on the door.

What carries the guarantee is tests/test_authorisation.py, which exercises the cases the Testing Report lists as TC-95 to TC-99 against the API. Its header states the standard plainly: if one of those tests fails, it is a data leak, not a failing test. The database keeps every constraint, trigger and state machine it had those protect the integrity of the record, which is a different job from deciding who may read it.

9.5 The AI credential that does not exist

In v1.0 the model was called from the browser with a key the browser could read. The plan was to move that call server-side so the key stayed on the server. What was built removes the key entirely: the App Runner instance role carries bedrock:InvokeModel scoped to one inference profile, and the AWS SDK obtains short-lived credentials from the instance metadata service at call time.

The practical difference is that there is no secret to leak from this system, no rotation schedule to keep, and nothing to revoke if the repository were ever made public. Withdrawing this system's access to the model is a change to one IAM policy.

Every AI feature returns nothing on any failure, and the caller shows its documented fallback message. A clinical action is never blocked on a model response; and the safety rules that block a contraindicated prescription are deterministic code rather than a model, so they give the same answer every time and can be reproduced by hand.

10. User interface design

10.1 Design principles applied

PrincipleHow it shows up in the interface
One screen per taskA doctor completes an entire consultation, including every order, without leaving one screen. Staged orders are visible while the note is being written.
Show the queue, not a menuEvery clinical role lands on the work waiting for them, not a dashboard of links. The next action is always the top item.
Status by colour and wordEvery status carries both a colour and a text label, so it survives printing and colour blindness.
Monospaced clinical valuesBlood pressure, results, amounts and MRNs use a monospaced face so digits line up and misreadings are less likely.
Safety interrupts, not warnings buried in textAn allergy conflict blocks the action and states the reason in place. A critical result appears as a banner at the top of the doctor's dashboard.
Confirm every writeEvery action that changes the record produces a visible confirmation within a second, so staff never wonder whether it saved.
Mobile for one personThe patient application assumes one thumb, one hand and poor lighting. Five tabs, no nesting deeper than two levels, targets at least 44 pixels.
