1. Maintainability built in

Software that cannot be changed is finished the day it ships. Three decisions in version 1.0 exist mainly to make later change cheap.

DecisionWhat it buys the maintainer
Storage behind an interface the domain ownsReplacing browser storage with a server database touches one construction point, not the screens. Section 4 sets out that migration.
Rules separated from screensA change to the acuity thresholds or the interaction list happens in one place and takes effect everywhere it is used.
Reference data in named tables, not scattered literalsAdding a laboratory test, a drug or a ward is a data edit, not a code change.

One honest caveat. Version 1.0 has no automated test suite; the 110 cases in the testing report were executed by hand. That is affordable for a project this size but it will not stay affordable. Automating the rules-layer tests is the first item in the roadmap for exactly that reason.

2. The four kinds of maintenance

2.1 Corrective maintenance

Fixing what is broken. A P-grade is a response priority, decided when a fault is triaged, and it is not the same thing as the discovery severity recorded in the testing report. Severity describes what the fault could do; priority decides when we fix it, taking into account whether a workaround exists. A Major defect with no workaround can outrank a Critical one that is already contained.

GradeMeaningResponseExamples from our own defect log
P1Patient safety or data integrity at stake, no workaroundSame day, hotfixD-02 and D-04, both logged Critical. D-01, logged Critical, was P1 because every action button was unusable.
P2Blocks a department from workingWithin 3 working daysD-03 and D-14, both logged Major.
P3Wrong or confusing, but a workaround existsNext scheduled releaseD-11, logged Major but contained because staff could convert manually. D-05, D-06 and D-07, all Major.
P4Cosmetic or convenience onlyWhen convenientD-08, D-10, D-12 and D-13, all logged Minor.

2.2 Adaptive maintenance

Keeping up with a world that changes around the system.

TriggerWork it causes
NHIS changes its claim format or tariffsUpdate the claim fields and the price table. Reference data, not code.
A Mobile Money provider changes its APIChange the payment adapter only. The cashier screen and the audit entry are untouched.
Hospital adds a ward, department or imaging modalityAdd rows to the reference tables.
Data protection guidance tightensReview retention rules and consent wording, and extend the audit fields if required.
Browsers drop or change a featureTest against the current release each quarter and adjust.

2.3 Perfective maintenance

Making a working thing better, usually because users asked. Requests come from three places: the hospital's own suggestion route, patterns in the audit log showing where staff repeat themselves, and observations from usability sessions like those in the testing report.

Improvement already identifiedWhere it came from
Keyboard-only entry for the vitals formNurse participant P1 was slowed by reaching for the mouse mid-form
Save a partly written consultation as a draftRaised in acceptance testing. A doctor called away mid-consultation loses the note today.
Bulk verification of routine laboratory resultsThe laboratory representative verifies each result individually, which is slow on a busy morning
Printable ward round sheetNursing request. The ward board is on screen only.

2.4 Preventive maintenance

Work nobody asked for, done so that later work stays possible.

ActivityFrequencyPurpose
Dependency and browser checkMonthlyCatch a deprecation before it becomes an outage.
Restore rehearsalQuarterlyA backup nobody has restored is a hope, not a backup.
Audit log reviewMonthlySpot shared logins and unusual access patterns.
Reference data auditQuarterlyRemove discontinued drugs and tests before somebody orders one.
Safety rule review with a pharmacistEvery six monthsThe interaction list is a fixed set today. It must be reviewed by somebody qualified, and not left to drift.
Dead code and duplication sweepEach releaseKeep the codebase legible for the next maintainer.

3. Working practices

3.1 Bug-fixing process

  1. Report. Anybody can raise a fault. The report needs the role, the screen, what was expected, what happened, and the MRN if a patient record is involved.
  2. Reproduce. A fault that cannot be reproduced is not fixed, only guessed at. Reproduce it on test data first.
  3. Grade. Assign P1 to P4 by clinical consequence using §2.1.
  4. Find the cause. Fix the cause, not the symptom. D-05 looked like a display problem and was actually a stale copy of the inventory list.
  5. Write the test first. A case that fails before the fix and passes after it.
  6. Fix on a branch. One branch per fault, named for the fault number.
  7. Review. Another group member reads the change. No self-merging.
  8. Retest and regress. Run the new case plus every case touching the same module.
  9. Release and record. Merge, deploy, and close the entry with the resolution written down as in §9 of the testing report.

3.2 Version control

PracticeRule
RepositoryGit, one repository, hosted remotely. Every group member has a clone.
Branchesmain is always deployable. feature/name for new work, fix/defect-id for faults.
CommitsOne logical change per commit. The message says what changed and why, not "update".
MergingPull request, reviewed by another member, then merge. Never commit directly to main.
TagsEvery release tagged v1.0, v1.1 and so on, so any deployed version can be recovered exactly.
SecretsNo API key, password or connection string in the repository. Environment variables only. This rule has no exceptions.

3.3 Versioning and releases

Semantic versioning. The major number changes when the data model changes in a way that needs migration. The minor number changes when features are added. The patch number changes for fixes only. A hospital needs to know from the version number alone whether an upgrade will touch their data.

Release typeCadenceContents
HotfixAs neededP1 faults only. Deployed the same day, announced afterwards.
PatchMonthlyP2 and P3 faults, small perfective changes.
MinorQuarterlyNew features from the roadmap. Announced two weeks ahead with a note of what changes on which screen.
MajorAnnually at mostData model changes. Requires a migration plan, a rehearsal on a copy of the database, and a rollback path.

3.4 Dependency and library updates

Version 1.0 deliberately carries almost no third-party code. Fonts and an icon font are the only external assets, and both are pinned to a specific version and do not track latest. When the server backend arrives in v2.0 the dependency count rises sharply, so the rule from that point is: security patches applied within a week, minor upgrades reviewed monthly, major framework upgrades treated as their own piece of work with its own test pass. Never upgrade a dependency and ship a feature in the same release; when something breaks you will not know which change did it.

3.5 Security updates

AreaOngoing obligation
AuthorisationThe v1.0 weak point, stated plainly in the testing report: authorisation is enforced in the application, not the database. §4 step 2 closes it. Until then, treat the deployment as a demonstration, not a live clinical system.
CredentialsRotate staff passwords each semester or on any suspicion. Remove accounts the day somebody leaves, not at the end of the month.
SecretsRotate API keys quarterly. Move the AI key server-side as part of §4 step 5 so it never reaches a browser.
TransportHTTPS only. No mixed content.
AuditReview the log monthly for shared logins and out-of-hours access.
DisclosureA named contact for reporting a vulnerability, and a commitment to acknowledge within two working days.

4. Migration to a server database

This was the single most important piece of post-submission work. It has been done, and this section is now a record of what was carried out, not a plan. Version 1.0 persisted to browser storage, so a record did not follow a patient between devices and authorisation was enforced only in the application; both were consequences of the same missing piece. The table below keeps the original six steps and their acceptance criteria, with the outcome against each.

StepWorkDetail and acceptanceOutcome
1Create the schemaThe sixteen entities from the design document's data model, as PostgreSQL tables with the constraints listed there: unique MRN, unique occupied bed, append-only audit table, invoice status derived, never stored. Accepted when the seed data loads and every constraint rejects the case it exists to reject.Met. Sixteen tables with every constraint named. Verified by loading the seed data and confirming that each constraint rejects the case it exists to reject: nine constraints, nine rejections.
2Move authorisation into the databaseStaff accounts in a managed authentication service, with each role mapped to row-level security policies. A cashier's query for a clinical table returns no rows regardless of what the client asks for. Accepted when the security cases TC-95 to TC-99 pass against the database directly, not through the interface.Met, then changed. Row-level security was built and its acceptance criterion was reached: twenty policy checks passing against the database directly. It was then replaced by guards in the API, for the reasons in the design document. TC-95 to TC-99 now pass against the API instead, along with five further cases the move made necessary.
3Write the server adapterA second implementation of the same repository interface, calling REST endpoints instead of browser storage. Accepted when the existing integration cases pass unchanged.Met. HttpRepository satisfies the same interface, and the existing integration cases passed unchanged.
4Switch the adapterChange which adapter is constructed at the single point where that happens. No screen, domain class or application component is modified. Accepted when the full system test set passes with data shared across two devices.Met. One line changed. No screen, domain class or application component was modified, and the same data is now visible from any device.
5Move AI calls server-sideRoute completions through a server endpoint so the API key never reaches a browser. Accepted when no key appears in any client request.Exceeded. No key exists to reach a browser: the service reaches the model through its compute role, so there is no long-lived AI credential anywhere in the system.
6Backup and restoreAutomated daily backup with point-in-time recovery, and a documented restore procedure. Accepted only after a restore has actually been performed onto a fresh instance.Partly met. Automated daily backups with seven-day point-in-time recovery are configured and deletion protection is on. The acceptance criterion is stricter than that, and rightly so: it is met only once a restore has actually been performed onto a fresh instance. That has not been done, so this step remains open and is the first item of remaining work below.

The reason this was a swap and not a rewrite is the dependency direction in the architecture: the repository interface belongs to the domain, so the domain neither knows nor cares which adapter satisfies it. The claim was made before the work and held during it, which is the useful kind of architectural claim.

What remains. Three things, in order of importance. First, perform a restore onto a fresh instance and time it, which is the only way step 6 can honestly be closed. Second, run the deployment from an account with permissions scoped to this project instead of from the account root, which is convenient for a capstone and wrong for anything else. Third, put the four verification suites into a build that runs on every push, so that a missing route guard is caught by the pipeline, not by someone remembering to run a script.

5. Scalability

Version 1.0 was designed against 5,000 patient records, 100 concurrent staff and twelve months of history. Beyond that, the constraints and their answers are as follows.

Pressure pointLimit in v1.0Response when it is reached
Patient register sizeSearch stays inside its 300 millisecond target to roughly 5,000 recordsMove search to indexed database queries with pagination. Already covered by step 1 of the migration.
Concurrent staffNo server, so no shared contention todayConnection pooling and read replicas. A hospital of 100 staff will not need more than one primary.
Clinical history growthTimeline renders fully; long histories will slow itPaginate the timeline and load older entries on demand.
Audit log growthGrows without boundPartition by month, archive partitions older than the statutory retention period to cold storage.
Multiple facilitiesSingle facility onlyAdd a facility identifier to every record and scope row-level security by it. This is a major version change because it touches the data model.
Peak load at clinic openingUntested above 100 sessionsLoad test before any expansion. Static hosting scales; the database is the ceiling.

6. Future evolution roadmap

6.1 Why this order

The tempting order is the opposite one: add features people can see, defer the database. We have put the database first deliberately. Every item in v2.5 and v3.0 increases the amount of real patient data flowing through the system, and it would be irresponsible to increase that flow while authorisation still lives in the application layer. Boring infrastructure before visible features, in this domain, is a safety decision, not an engineering preference.

6.2 Notable items explained

ItemReleaseWhat it involves and why it matters here
Automated test suitev1.1The 110 manual cases become code for the rules layer first, since that is where a silent regression is most dangerous. Without this, every future release costs a full manual pass.
Live Mobile Moneyv2.0Replace the modelled provider step with a real collections API and a merchant account. The cashier's screen does not change, only the adapter behind it.
SMS remindersv2.5In-app notifications only reach patients who open the application. An SMS reaches a patient with a basic phone, which in this setting is most of them.
Offline-capable mobilev2.5Cache the patient's own records so appointments and results are readable with no signal, syncing when the connection returns. This matters more outside the cities than any new feature would.
Twi and Ga interfacev2.5Translate patient-facing screens and notifications. Staff screens stay in English, which is the working language of clinical documentation.
NHIS electronic submissionv2.5Submit claims directly instead of exporting them. Depends entirely on what the Authority exposes, so it is scoped as investigation before commitment.
HL7 device feedsv3.0Analysers write results straight into the record, removing the transcription step and the errors that come with it.
DICOM viewerv3.0View the actual images beside the report, not the report alone.

7. Technology migration

No technology choice in version 1.0 is permanent, and none of them locks the system in. What follows is the migration path for each layer if it needs to change.

LayerTodayIf it must change
InterfaceComponent-based JavaScript in the browserScreens are the most replaceable part because they hold no state of their own. A framework change is a rewrite of presentation only, with the domain and rules untouched.
StorageBrowser storage behind the repository interfaceAlready planned: PostgreSQL in v2.0. The interface means a further change, to a different database, is another adapter, not another migration.
AuthenticationApplication-levelManaged service in v2.0. If the hospital later runs its own directory, the service is swapped behind the same role mapping.
AI providerOne completion endpoint over HTTPSAll calls go through a single adapter, so a different provider or a locally hosted model is one file. Worth revisiting if data residency rules tighten.
HostingStatic hosting with builds from the repositoryThe build output is plain static files, so it moves to any host, including a server inside the hospital if a policy requires it.
PaymentsModelled provider flowAdapter pattern already in place for exactly this reason.

9. Further AI and emerging technology

Version 1.0 already uses AI in six places, all of them advisory. The candidates below are ordered by how well the value is understood, not by how impressive they sound.

CandidateConfidenceAssessment
No-show predictionHighPredict which appointments will be missed from history, and overbook those slots deliberately. Low clinical risk, direct effect on clinic throughput. The obvious first addition.
Stock demand forecastingHighForecast drug demand from dispensing history and season. Prevents both stockouts and expiry write-offs. No patient-facing risk.
Coding assistance for claimsMediumSuggest diagnosis and procedure codes from the encounter note. Reduces rejected claims. Needs a human to confirm every code.
Deterioration early warningMediumFlag inpatients whose vitals trend towards deterioration before it is obvious. Clinically valuable and clinically risky. Requires validation against real outcomes and a clinician's sign-off, not a student project's judgement.
Voice dictation for notesMediumFaster documentation, but accuracy on Ghanaian English and local drug names would need testing before anybody relied on it.
Image pre-readingLowDraw a radiologist's attention to regions of interest. Regulated territory. Not appropriate without formal clinical validation and approval.
Autonomous clinical decisionsExcludedNot on the roadmap at any release. Every AI feature in this system requires a human to accept it, and that constraint is deliberate and permanent.

10. Handover

For the system to survive its authors, the following must be in the hospital's hands, not only in ours.

  1. Repository access transferred to a hospital-owned account, with our accounts retained only as contributors.
  2. Every credential rotated at handover, so no student password remains valid.
  3. This document, the design document and the user manual held by the IT office in their current versions.
  4. The defect log carried forward, not archived. It is the fastest orientation a new maintainer can get.
  5. A named owner inside the hospital for each of: user accounts, backups, and the pharmacist review of safety rules.
  6. A walkthrough session with the IT office covering deployment, restore, and the migration plan in §4.

The most likely way this system fails is not a technical fault. It is nobody owning it after the semester ends. The list above exists to make that outcome harder.
