Version1.0 final, August 2026

The system replaces the fragmented paper process of a district hospital with one shared patient record that every department reads from and writes to. It covers the full journey from registration through triage, consultation, laboratory and imaging, pharmacy, ward admission, discharge and billing, and it gives patients a mobile application for their own part of the record.

Two applications are served from one deployment: a staff workspace for eight roles, and a patient application. Both run on the same domain model, so a booking made on a phone is the same record the front desk sees.

2. Main system features

AreaWhat it does
Patient administrationRegistration with automatic MRN allocation, demographics, blood group, allergies, chronic conditions, insurance, and search by name or MRN
AppointmentsDoctor rosters with real slot availability, double-booking prevented, check-in, walk-ins, automatic follow-up booking
TriageVitals entry with an acuity suggestion computed from the readings, and queue ordering by urgency
Consultation and EMROne screen for complaint, diagnosis, notes and every order type. Patient chart with timeline, vitals trend, results, medications, billing and documents
DiagnosticsLaboratory and imaging ordering with STAT priority, a four-stage sample pipeline, verification-gated release, critical result escalation to the ordering doctor
PharmacyElectronic prescribing with allergy and interaction blocking, dispensing with automatic stock decrement, low-stock and expiry warnings
InpatientWard and bed board, admission, medication administration record, discharge with an automatically generated summary
BillingCharges captured from clinical events as they happen, cash and Mobile Money payment, printable receipts, insurance claims through to payment
AdministrationHospital KPIs, live activity feed, plain-language operations assistant, staff directory, append-only audit log
AI assistanceSix advisory features: consultation drafting, result explanation for clinicians and for patients, claim justification drafting, operations queries, and a patient symptom checker
Patient mobileOnboarding, login, booking, records, alerts, profile, Mobile Money payment, symptom checker

Cross-cutting: role-based access with explicit restriction notices, keyboard command palette, printable clinical and financial documents, persistence across browser restarts, and a reset control for demonstration.

3.1 Signing in

  1. Open the application URL in Chrome, Edge, Firefox or Safari. Nothing needs installing.
  2. On the login screen, select a role button. The email field fills in automatically.
  3. Enter the password from Links.txt and select Sign In.
  4. A short welcome panel explains the role. Select Get started.

To change role, sign out at the bottom of the sidebar and pick another. The nine accounts are: patient, doctor, nurse, receptionist, laboratory technician, radiologist, pharmacist, cashier and administrator.

Starting clean. The system remembers state between visits. If you want the original seeded data back at any point, select Reset demo data on the login screen.

5. Technology stack

LayerTechnology
InterfaceHTML5, CSS3, component-based JavaScript. No installation or plugin required on client machines.
Application logicJavaScript classes with explicit state and lifecycle, holding all business rules
Domain modelSixteen entities with their invariants, plus state machines for order, invoice and claim lifecycles
PersistenceBrowser storage behind a repository interface owned by the domain. PostgreSQL adapter planned for v2.0.
AI servicesLarge language model over HTTPS, called through a single adapter
PrintingBrowser print pipeline with print stylesheets
HostingStatic hosting with automatic builds from the source repository, served over HTTPS
Version controlGit. Branch per feature or defect, pull requests reviewed, releases tagged.

Architecture is four layers with dependencies pointing downward only: presentation, application logic, domain model, persistence. Because the persistence interface belongs to the domain, the storage implementation can be replaced without touching any layer above it.

8. Known limitations

Stated up front so you do not have to find them.

LimitationDetail
No server databaseVersion 1.0 persists to browser storage. Records do not follow a patient between devices, so two browsers hold two separate datasets. The migration to PostgreSQL is specified in six steps with acceptance criteria in the maintenance plan.
Authorisation in the application layerRole-based access works as tested, but it is enforced by code the client runs rather than by the database. Treat this deployment as a demonstration, not a live clinical system holding real records. Moving authorisation into row-level security policies is the first item of post-submission work.
Mobile Money is modelledThe provider request and approval sequence is faithful and the records it produces are correct, but no real money moves. Live collection needs a merchant agreement a student project cannot obtain. The replacement point is documented.
No automated test suiteAll 110 test cases were executed manually. Automating the rules layer is the first roadmap item.
Interaction checking is a fixed listCovers common high-risk drug pairs and recorded allergies, not a full pharmacological database. Scheduled for six-monthly review by a qualified pharmacist.
AI features need internetThey degrade gracefully with a plain message and never block a workflow, but they are unavailable offline.
Single facility, English onlyNo multi-site operation and no local-language interface yet. Both are on the roadmap.
Performance measured to 5,000 recordsBehaviour above that is projected rather than measured.

9. Special instructions

  1. Use the walkthrough in §4 in order. Each step hands work to the next role, which is the point of the system. Opening screens at random will not show you the handovers.
  2. The AI features are live. They call a real service and need internet. If one reports itself unavailable, the connection is down; every other function continues to work, which is the designed behaviour and is tested.
  3. Blocked actions are the system working. A refused prescription, a struck-through slot, a locked clinical tab and a refused signature are all enforced rules, not faults.
  4. Purple means AI. Anything purple with a sparkle mark is an advisory suggestion that requires a human to accept it. Nothing purple writes to the record on its own.
  5. To see mobile properly, open the patient application on a phone, or narrow the browser window to about 400 pixels.
  6. Credentials are in Links.txt only, never in the repository. Please do not redistribute them.
  7. Reset demo data on the login screen restores the seeded baseline if you want to repeat the walkthrough from the start.
