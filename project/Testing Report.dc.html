2. Test strategy

We tested in the order the software was built, from the inside out. Business rules were checked first in isolation, because a wrong rule invalidates every test above it. Then module handovers, then whole journeys, then the qualities in the non-functional requirements. Nothing was signed off on inspection alone. Every case has a recorded expected and actual result.

Priority was risk-based. A hospital system can cause real harm in three places: a wrong drug reaching a patient, a critical result not reaching a doctor, and one patient's record appearing under another patient's name. Those three paths were tested hardest and carry the most cases.

LevelApproachEntry and exit criteria
UnitWhite box. Each rule called directly with boundary and invalid inputs.Enter when the rule is implemented. Exit when all boundary cases pass.
IntegrationGrey box. Trigger an action in one module and assert the effect in another.Enter when both modules pass unit tests. Exit when every handover in the component diagram is proven.
SystemBlack box. Complete journeys performed as a real user would, switching roles.Enter when integration passes. Exit when all nine roles complete their journeys with no data loss.
FunctionalRequirement checklist walked one line at a time.Exit when every SRS requirement is confirmed present and correct.
UsabilityTask-based observation, five participants, think-aloud protocol.Enter when the interface is feature complete. Exit when every task is completed unaided inside the target time.
PerformanceBrowser timing instrumentation on the ten most-used screens.Exit when NFR-01 and NFR-02 targets are met.
SecurityAutomated. Every case is asserted against the API with each role's token, and again through the browser-facing surface over cookies.Exit when no clinical or financial data is reachable without the right role, and when the suites pass in the build.
AcceptanceRole representatives run their own daily work and sign off.Exit when every representative signs.

8.1 How these cases are now run

In v1.0 the ten security cases above were checked by hand, through the interface. That was the honest weakness this report named: the controls worked as tested, but they were enforced by code the client ran, and a manual pass proves only that nobody clicked the wrong thing on the day.

They are now automated, and they run against two different surfaces so that neither can quietly stop protecting anything.

SuiteCasesWhat it proves
tests/test_authorisation.py19The API refuses what it should, called directly with each role's token. This is the suite that replaced row-level security, and its header states the standard: if one of these fails, it is a data leak, not a failing test.
tests/test_staff_admin.py, test_corrections.py, test_account_prefs.py36Account creation and deactivation, self-service passwords, record correction, and the reset request. Added in the final revision alongside the features themselves.
tests/test_journey.py and the rest19The clinical workflow end to end, plus the deterministic safety rules and the state machines. 74 backend tests in total, running in about two seconds. With the two operational suites and the screen sweep, 194 checks run against a deployment.
scripts/verify-e2e.sh39The same guarantees through the browser-facing surface: cookies, redirects, sign-in for all nine roles, and TC-96 and TC-99 asserted against rendered HTML, not against JSON.
scripts/verify-operations.sh25Stock, catalogues, wards, rosters, reports and messages, each exercised against a running API with the role that owns it and at least one role that does not.
scripts/verify-records.sh23Appointments, clinical corrections, billing and portal access, end to end and in order, because several of them consume state.
scripts/verify-screens.sh33Every screen loads as the role that owns it. A server component that throws renders as a generic error page, which is easy to miss by clicking around; this is the check that none is broken.

Two defects were found by these suites during the migration before any reader could, which is the point of writing them. The patient booking screen returned a server error because it asked for the staff directory, which is staff-only; it now asks for bookable doctors instead, and TC-103 pins that. Separately, the first version of the TC-96 assertion was wrong, not the code: it searched the chart the cashier sees for a test name, but "Lipid Panel" is also the description of a billed line, so a cashier seeing that string is correct. The assertion now uses a result value and a drug name, neither of which reaches the cashier. The first is recorded as D-20.

What is still not claimed. These suites prove the controls this team thought to test. They are not a penetration test, and no independent security review has been carried out. The system holds synthetic data only.

11. Conclusion

All 110 test cases pass and all 14 defects are closed. Every functional and non-functional requirement in the SRS has at least one executed case behind it.

Two things we would do differently. First, we tested persistence late, and D-14 was the result. Had we written the reload case at the start we would have built the persistence layer before the screens depended on it. Second, D-01 and D-09 both came from assuming external resources would be reachable in the deployed environment. Testing the deployed build early, not just the development build, would have caught both in an afternoon.

The security limitation in §8 is the honest weak point of version 1.0 and we have not dressed it up. Authorisation works, but it lives in the application. Moving it into the database is the first item of post-submission work.
